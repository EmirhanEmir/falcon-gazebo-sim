## Status legend (new, this pass — replaces the prior matrix's `READY`/`READY_WITH_CALIBRATION`/`BLOCKED_DATA_REQUIRED`/`NOT_YET_IMPLEMENTED` legend)

| Status | Meaning |
|---|---|
| `READY_FOR_V1` | Data is `CONFIRMED`/settled; no further data-collection or sign-verification is needed before this item can be used in a V1 SDF/plugin implementation as-is. |
| `READY_WITH_V1_PROVISIONAL_MODEL` | Real, usable numeric data or an equation-complete architecture exists and is explicitly usable for V1 now, but the source itself (or this assessment) flags it as not-yet-final (`V1_PROVISIONAL`, `V1_CALIBRATED`, `DERIVED_WITH_STRONG_EVIDENCE`, or an explicitly-authorized V1-estimate path) — distinct from a data blocker: something can be built and tested now, subject to a documented, non-final caveat. |
| `READY_BUT_REQUIRES_SIGN_TEST` | The data/architecture/derivative itself exists and is not in question — only the mapping of a documented convention (XFLR5 sign, mesh axis, inertia off-diagonal sign, etc.) onto Gazebo's own joint/body/force sign convention remains unverified. This is a test-to-run gate, not a data-collection gate. |
| `BLOCKED_DATA_REQUIRED` | Cannot proceed at all without additional data that is currently missing outright — no numeric value, table, or measurement exists anywhere in the repository to build from, and no calibration/estimate path is authorized in its place. |
| `NOT_YET_IMPLEMENTED` | No substantive engineering work or design decision has been made on this item at all — distinct from `BLOCKED`: this is a strategy/implementation choice nobody has proposed or evaluated yet, not a missing-data problem. |

**Critical rule applied throughout this matrix (per task instruction):** `BLOCKED_DATA_REQUIRED` is never used merely because implementation code hasn't been written yet. Data readiness and implementation status are tracked separately — e.g. collision geometry has no data blocker at all (it is `NOT_YET_IMPLEMENTED` because no strategy has been chosen), while inertia now has real V1 data (`READY_WITH_V1_PROVISIONAL_MODEL`, not `BLOCKED_DATA_REQUIRED`, even though no SDF file exists yet either).

## Summary

Compared to the pre-master-dataset matrix, the center of gravity of this project's readiness has shifted substantially: **mass, CG, inertia, hub/thrust-axis placement, motor electrical parameters, propeller physical identity, longitudinal aerodynamics, lateral-directional aerodynamics, control-surface derivatives, drag, hinge geometry, and battery V1 data are all now either `READY_FOR_V1` or `READY_WITH_V1_PROVISIONAL_MODEL`/`READY_BUT_REQUIRES_SIGN_TEST`** — a full V1 numeric model can be attempted for nearly every subsystem except propeller aerodynamic loading. Two genuine, still-missing-data blockers remain (the APC Ct/Cp table and the ArduPilot channel mapping/SITL artifacts), and one item remains an undecided design choice rather than a data gap (stall/post-stall model). Every `READY_BUT_REQUIRES_SIGN_TEST` item converges on the same small set of future tests already registered in `tests/gazebo/README.md`: `AOA_SIGN_TEST`, `SIDESLIP_SIGN_TEST`, `ELEVATOR_TEST`/`AILERON_TEST`/`RUDDER_TEST`, and a reaction-torque/pitch-moment sign check folded into `REACTION_TORQUE_TEST`.

**Update, 2026-08-21 (first Gazebo structural implementation pass):** `model/model.sdf` now exists and is `Valid.` per `gz sdf --check` — collision geometry (row 7), link structure (row 8), and control-surface hinge axes (row 9) have moved from "data/strategy ready" to **actually implemented**, closing the "collision geometry design choice" and "hinge-axis fitting" items previously listed under "True Remaining Blockers"/"V2-only" below. The remaining true blockers are unchanged: the APC Ct/Cp table, the `CL0`/`Cm0` derivation, the ArduPilot/SITL artifacts, and the full set of sign tests (now runnable against a real joint set for the first time).

**Update, 2026-08-22 (`AERODYNAMICS_V1_IMPLEMENTATION` pass):** the aerodynamic force/moment V1 model is now **implemented** — `plugins/aerodynamics/` (a `gz-sim8` C++ System plugin, `FalconV2Aerodynamics`) is attached to `model/model.sdf` via one additive `<plugin>` block (no structural element modified), reads the 5 real control-surface joint positions and `base_link`'s velocity/pose from the ECM, and applies the resulting force at the CG / moment as a pure torque each `PreUpdate`. `CL0`/`Cm0` are now `DERIVED` (closing blocker item 3 below).
